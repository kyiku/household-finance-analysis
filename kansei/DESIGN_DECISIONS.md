# 家計クラスタ比較アプリ 改修の意思決定記録

日付: 2026-08-16
対象:（Streamlit アプリ + 家計調査データ分析）

## 背景

- 元々の目的（`notebooks/kakei_data_fetch.ipynb` 冒頭に記載）は
  「家計簿アプリのユーザー支出傾向を総務省『家計調査』と比較し、**貯蓄できている人の特徴**を分析する」こと。
- 改修前のアプリは「貯蓄・負債の比較」止まりで、取得済み5データセットのうち
  2つ（年齢別収支、貯蓄内訳）が未使用。黒字率データも使われておらず、元々の目的に答えていなかった。
- 「適切なデータセットからデータ分析をする課題」として、データ活用・分析の妥当性・見せ方を
  まとめて改善する方針をユーザーが承認（フル改修）。

## 決定事項と理由

### D1. 未使用データセットをアプリに取り込む

**決定**: `kakei_income_expense_by_age.csv`（年齢別 実収入・消費支出・黒字率）と
`kakei_savings_breakdown_by_age.csv`（年代別 貯蓄内訳）を `kansei/data/` に追加し、
「貯蓄できている人の特徴」タブで使用する。

**理由**: 元々の分析目的に直結するデータが取得済みなのに使われていなかった。
黒字率（可処分所得に対する黒字の割合）は「貯蓄できているか」の最も直接的な指標。

### D2. ベンチマークは「全期間平均」ではなく「各グループの直近1年」を使う

**決定**: ユーザーとの比較に使う年代別・収入階級別のベンチマークは、
全時期の平均ではなく「**各グループで公表済みの直近1年分**（四半期データは4期、月次データは12か月）」
の平均を使う（`src/benchmark.py: latest_mean_by`）。

**理由**: データは2000年〜2026年の約26年分。全期間平均だと2000年代前半の水準が混ざり、
「今のあなた」と比較する基準として不適切。
当初は「最新の暦年」でフィルタする実装だったが、コードレビューで
(1) 2026年はQ1しかなく季節バイアス（ボーナス期を含まない）で黒字率が最大10pt歪む、
(2) 収支データは若年層の2026年分が未公表で暦年フィルタだとNaNになり、
グラフの欠落・「29歳以下」の黒字率診断の機能停止を起こすことが判明。
グループごとのローリング窓に変更した（回帰テストを `tests/test_analysis.py` に追加）。

### D3. 時期コードをパースして時系列を復元する

**決定**: e-Stat の時期コード（例: `2025001012` = 2025年10〜12月期）をパースする
`periods.py` を作り、年・四半期を列として持たせる。

**理由**: 改修前は `aggfunc="mean"` で時期を潰しており、24年分の変化が見えなかった。
コード体系は `YYYY` + `00` + 開始月2桁 + 終了月2桁 と確認済み（月次データは開始月=終了月）。

### D4. 「クラスタに分類されました」という表現をやめる

**決定**: KMeans クラスタリングは「家計タイプマップ（参考）」として残すが、
以下を明示する:
- サンプルは**世帯ではなく「収入階級×四半期の集計値」**（18階級×96期=約1,700点）であること
- 個々の世帯のばらつきは反映されていないこと

主役の診断は「同収入階級の最新平均」「同年代の最新平均」との比較（統計的に正直な提示）に変更。
クラスタ番号ではなく特徴に基づく名前（例: 高収入・高貯蓄型）を自動付与して解釈可能にする。

**理由**: 集計値をクラスタリングした結果を「あなたはクラスタ2」と提示するのは、
個票データでの分類のような印象を与えミスリーディング。課題としても
「データの性質に合った分析手法の選択」を示す方が適切。

### D5. 黒字率診断のために任意入力（手取り月収・月間支出）を追加

**決定**: 診断タブに任意入力として「手取り月収」「月あたり消費支出」を追加し、
入力があれば本人の黒字率を計算して年収五分位・同年代の黒字率と比較する。

**理由**: 黒字率 = (可処分所得 − 消費支出) / 可処分所得。既存入力（年収・貯蓄・負債）だけでは
フロー（毎月貯蓄できているか）が分からない。ストック（貯蓄残高）とフロー（黒字率)の両面で
「貯蓄できているか」を診断できるようにする。必須にしないのは入力障壁を上げないため。

### D6. モジュール分割とテスト

**決定**: `app.py` 一枚岩（約150行、ロジックとUI混在）をやめ、
純粋ロジックを `src/` に分離。pytest でユニットテストを書く。

- `src/periods.py` — 時期コードのパース
- `src/data_loader.py` — CSV読み込み・整形（純粋関数、DATA_DIR は引数）
- `src/features.py` — 比率計算・収入階級判定・入力検証
- `src/benchmark.py` — 最新年ベンチマーク・比較表
- `src/clustering.py` — 家計タイプマップ（KMeans + 自動命名）
- `src/analysis.py` — 「貯蓄できている人の特徴」用の集計

**理由**: ロジックをUIから分離しないとテスト不能。コーディング規約
（小さいファイル・高凝集・イミュータブル・入力検証）にも沿う。
UI層（`app.py`）は Streamlit の `AppTest` でスモークテストのみとし、
カバレッジ対象は純粋ロジックに限定する（UIの描画細部のテストは費用対効果が低い）。

### D7. タブ構成

**決定**: 3タブ構成にする。

1. **あなたの家計診断** — 入力 → 同収入階級・同年代・(任意)黒字率の比較 + 家計タイプマップ(参考)
2. **貯蓄できている人の特徴** — 年収五分位別の黒字率・平均消費性向、年代別黒字率、
   年代別の貯蓄内訳（有価証券比率など）。データから言えることを注記付きで文章化。
3. **データとトレンド** — 使用データの説明、年代別貯蓄・負債の時系列、黒字率の長期推移
   （出典・集計単位・注意点を明記）

**理由**: 「個人の診断」（改修前の機能の改良）と「データセット全体からの知見」（課題の本丸）を
分けることで、分析の主張が明確になる。

### D8. やらないこと（YAGNI）

- e-Stat API からの再取得・データ拡充（既存CSVで目的に答えられる。必要になったら別課題）
- DBやAPIサーバー化（Streamlit 単体で十分）
- 予測モデル（回帰・分類）の導入（集計データしかなく、個票がない以上、過学習した見せかけになる）
- git リポジトリ化・コミット（このディレクトリは git 管理外。方針変更はユーザー判断待ち）

### D9. コードレビュー指摘への対応（2026-08-16）

code-reviewer エージェントのレビュー（HIGH 2件・MEDIUM 5件・LOW 3件）に対応:

- **HIGH**: 「最新暦年」判定の破綻 → D2 のとおりローリング窓へ変更。回帰テスト追加。
- **HIGH**: 上記を検出できないテスト不足 → 「29歳以下」「NaNなし」等の回帰テストを追加。
- **MEDIUM**: KMeansの空クラスタ発生時にクラスタ番号とprofile行順の対応が崩れる → 明示的にRuntimeErrorを送出するガードを追加。
- **MEDIUM**: `pivot_table` 由来の `columns.name="項目"` が表示に混入 → `rename_axis(columns=None)` で除去（テスト追加）。
- **MEDIUM**: pivot時の重複行が暗黙に平均化される → 重複検出でValueError（テスト追加）。
- **MEDIUM**: `st.cache_resource` 共有オブジェクトの可変性 → モデルは読み取り専用で扱う旨をdocstringに明記。
- **MEDIUM**: 例外捕捉が `FileNotFoundError` のみ → `KeyError/ValueError/RuntimeError` も捕捉しユーザー向けメッセージ化。
- **LOW**: 貯蓄内訳構成比のゼロ除算ガード、`ui/trends.py` のロジック重複解消（`latest_mean_by` を再利用）、
  黒字率比較値がない場合のキャプションを原因決め打ちしない文言に修正。

また、正しい集計に直した結果「黒字率のピークは20代後半〜30代前半」という当初の記述が
データと矛盾する（実際のピークは30代後半〜40代前半の山型）と判明したため、
「特徴3」の本文・まとめをデータに合わせて修正した。

### D10. 目的の再定義と診断機能の強化（2026-08-17）

ユーザーとの議論で、このアプリの目的は **(a) 家計の立ち位置診断** であり、
「(b) 貯蓄できている人の特徴分析」ではないと確定。データと目的の適合を検証した結果:

- 家計調査の集計データは (a) に適合。(b) には個票が必要で不適合(生態学的誤謬)。
- (b) 向けに検討した「一般用ミクロデータ」(統計センターの擬似個票)は**見送り**。
  目的が (a) なら不要。将来 (b) をやる場合の選択肢としてここに記録しておく。

(a) を強化するため、e-Stat から2データセットを追加取得(`scripts/fetch_benchmark_data.py`):

1. **貯蓄現在高階級別の世帯数分布**(家計調査 0002210024、年次2002〜2025年、万分比)
   → 「平均との差」ではなく「**分布の下から◯%地点**」というパーセンタイル診断に格上げ。
   貯蓄分布は右に歪んでおり(2025年: 中央値約1,183万円 < 平均約1,900万円)、
   平均比較はユーザーの直感とズレるため。階級内は一様分布とみなす線形補間(`src/percentile.py`)。
   最上位の開区間(4000万円以上)では下限の累積割合を返す(=控えめ側に倒す)。

2. **世帯主の年齢×年間収入階級のクロス表**(2019年全国家計構造調査 0003443480)
   → 「**同年代×同収入**」ベンチマークを診断に追加(`src/cross_benchmark.py`)。
   年齢は10歳階級(30歳未満〜70歳以上)がアプリの年代6区分と完全対応。
   例: 40代×600〜650万円の平均貯蓄は約654万円で、全年代混在の同収入階級平均(約1,940万円)
   と3倍近く違う — 年齢調整の効果が大きいことを実データで確認。
   別調査・別時点(2019年)のため、家計調査の値と水準比較しない旨をUIに明記。
   未公表セル(若年×高収入など)は None を返し、UIは代替比較へ誘導する。

UI変更:
- 診断タブを6セクション構成に(①立ち位置分布 ②同年代×同収入 ③同収入階級 ④同年代 ⑤黒字率 ⑥タイプマップ)
- トレンドタブに「年代で絞った収入階級別グラフ」(年代セレクタ付き)と、
  収入階級別グラフへの誤読防止注記(低収入階級には高齢世帯が多い)を追加
- タブ②を「貯蓄できている人の特徴」から「**統計にみる貯蓄の傾向**」に改名。
  集計値で「人の特徴」を名乗るのは看板倒れのため、診断の補足資料に位置づけを変更。

### D11. 課題要件「分析手法」対応 — 擬似ミクロデータによる機械学習分析の追加（2026-08-17）

授業課題(チーム開発_AIProgrammingⅣ)は発表・提出物に「分析手法(モデルやアルゴリズムの説明)」を
必須としているが、D4/D10 で KMeans を参考扱いに格下げした結果、手法の柱が薄くなっていた。
「データを丸ごと変える」案は3回分の積み上げを捨てるため却下し、
**「集計データ(アプリ・診断用)＋個票データ(モデル用)の2層構成」**に拡張した。

**データ**: 統計センター「一般用ミクロデータ」(平成21年全国消費実態調査・十大費目、全世帯 45,811世帯)。
利用規約同意+利用者登録(学生・授業利用・4名)の上でダウンロード(`kansei/microdata/`)。
擬似データのため「実証研究の結果とみなせない」旨と出典
(「一般用ミクロデータ(平成21年全国消費実態調査)」(総務省統計局)を加工して作成)をUIに明記。

**設計判断**:
- 貯蓄額の変数がないため、目的変数は**貯蓄余力率 = 1 − 年間消費支出/年間収入(税込)**と定義
  (黒字率の近似。可処分所得ベースではない点を明記)。中央値以上を「貯蓄余力の高い世帯」(二値)。
- **リーク防止**: 収入・支出の金額そのものは目的変数の構成要素なので特徴量から除外。
  特徴量は**十大費目の支出構成比＋世帯属性(0/1×6)のみ** —
  「何にお金を使う世帯が貯蓄できているか」という行動の問いに答える設計。
- 集計用乗率(Weight)を学習・評価の sample_weight に使用。学習70%/検証30%(層化)。
- 学習は `scripts/train_saver_model.py` で事前実行し、アプリは結果CSVを読むだけ(起動を軽く保つ)。

**結果**(検証データ): ロジスティック回帰 AUC 0.765 / 決定木(深さ4) 0.742 / ランダムフォレスト **0.774**。
重要度上位: 食料比率・光熱水道比率・世帯主就業・住居比率・交通通信比率。
貯蓄余力の高い世帯は住居費比率(7.7%→4.6%)と交通・通信比率が低い。
食料・光熱の構成比が高いのは消費総額を絞ると必需品の割合が上がるため(解釈をUIに記載)。

これにより発表の「分析手法」は、KMeans(とその限界の批判的検討)→個票での分類モデル、
という手法選定のストーリーとして構成できる。
